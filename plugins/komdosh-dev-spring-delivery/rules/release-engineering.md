# Release Engineering Rules

These rules apply to any code, tag, or release artifact generated by the release plugin. Two tracks: **service** (microservices deployed to k8s) and **library** (shared Kotlin libraries published to Maven Central / GitHub Packages). Shared rules apply to both; track-specific rules apply only to one.

## Shared (both tracks)

### Conventional Commits

Every commit on a release branch MUST use the [Conventional Commits](https://www.conventionalcommits.org/) prefix. The release plugin reads commit messages to classify the bump type and group changelog entries.

| Prefix | Meaning | Bump signal |
|---|---|---|
| `feat:` | New user-visible capability | minor |
| `fix:` | Bug fix | patch |
| `perf:` | Performance improvement (no behaviour change) | patch |
| `refactor:` | Internal code change with no public effect | patch |
| `docs:` | Documentation only | none (skipped from changelog) |
| `test:` | Test-only changes | none |
| `chore:` | Build, deps, tooling | none |
| `ci:` | CI / pipeline changes | none |
| `BREAKING CHANGE:` footer or `feat!:` / `fix!:` syntax | Removes or changes existing behaviour | **major** |

Scope is encouraged: `feat(orders): add bulk-create endpoint`. Scopes group changelog entries.

### Semver

Version `MAJOR.MINOR.PATCH`:

- **MAJOR** — breaking change (see "What counts as breaking" below).
- **MINOR** — new functionality, backwards-compatible.
- **PATCH** — bug fixes, internal refactors, perf, docs.

The `detect-release-type` skill computes the recommended bump from commits since the last tag. The user may override; the agent records the override rationale in the release PR description.

### What counts as breaking

The definition differs sharply between tracks. See the per-track sections below — but in both cases, **silent breaking is forbidden**: any breaking change MUST be advertised via a `BREAKING CHANGE:` footer or `!` syntax in at least one commit.

### CHANGELOG format

The plugin maintains `CHANGELOG.md` at the project root (or service root for monorepo modules). Format follows [Keep a Changelog](https://keepachangelog.com/) with one section per release:

```markdown
## [v1.4.0] — 2026-05-04

### Added
- feat(orders): bulk-create endpoint (#123)

### Changed
- feat(orders): rename `customerEmail` → `email` in `CreateOrderRequest` (#127)

### Deprecated
- `OrderService.createLegacy(...)` — sunset in v1.6.0 (#125)

### Fixed
- fix(payments): handle 409 conflict from gateway (#129)

### Breaking
- feat!(api): remove `/api/v0/orders` endpoint group (#131)
```

Section ordering: Added · Changed · Deprecated · Fixed · Breaking · Removed · Security. Empty sections are omitted. The header line is `## [vX.Y.Z] — YYYY-MM-DD` (ISO 8601, no time component).

### Pre-release tags

`v1.4.0-rc.1`, `v1.4.0-beta.2`, `v1.4.0-alpha.3` are permitted. The plugin treats them as informational and does NOT advance the changelog. Final release is the unsuffixed `vX.Y.Z`.

### Release PR

Cutting a release ALWAYS goes through a PR titled `release: vX.Y.Z`. The release-coordinator opens it; the user reviews and merges. Direct pushes to the release tag bypass review and are forbidden.

## Service-track rules

### What counts as breaking (service)

A service release is breaking if **any of**:

- A migration changes a column or table in a way that pre-deploy code cannot read (e.g., dropping a NOT-NULL column, narrowing a type, renaming without a temporary alias).
- A public HTTP endpoint changes its URL, method, request shape, or response shape in a way that existing clients would observe.
- A consumed event's expected payload changes.
- A config key is renamed or removed without backwards alias.

Adding new endpoints, new optional fields, or new migrations that only add nullable columns is **not** breaking.

### Migrations and rollback decision tree

For each migration in a release window, classify rollback as one of:

| Class | Examples | Rollback strategy |
|---|---|---|
| **Mechanically reversible** | `ADD COLUMN nullable`, `CREATE INDEX`, `ADD CONSTRAINT` (deferrable) | Inverse DDL emitted in the playbook. |
| **Reversible-with-data-loss** | `DROP COLUMN`, `DROP TABLE` after data is no longer read | The plugin refuses to emit the inverse — surfaces "forward-fix only" with rationale, including a sketch of the forward-fix migration if the rollback fires. |
| **Type-narrowing or NOT NULL tightening** | `ALTER COLUMN ... NOT NULL` after backfill | Forward-fix only. The pre-deploy backfill ran with the old code; rollback must re-widen the column. |

The `produce-rollback-playbook` skill writes the playbook to `docs/release/playbooks/<version>.md`. The release coordinator surfaces ENV variables and feature flags that must move atomically with the rollback (e.g., "if rolling back v1.4.0, also flip `FEATURE_BULK_ORDERS` off").

### Feature flags

Service releases prefer **dark-launch behind a feature flag** for any non-trivial change. The release-coordinator surfaces flag dependencies in the readiness check; flags that are hard-coded `true` in the release should be flagged as candidates for removal in the next release.

### Smoke endpoints

Every service is expected to expose `/actuator/health` with `db` and key downstream indicators (per `core/rules/observability.md`). The readiness check confirms it returns 200 on the staging-equivalent profile.

## Library-track rules

### What counts as breaking (library)

A library release is breaking if **any of**:

- Removing or renaming a public symbol (class, object, function, top-level property) **without** a `@Deprecated(level = HIDDEN)` shim that preserves the binary signature for at least one minor version.
- Changing a public function's signature: parameter type, parameter count, return type, generic bound, suspending → non-suspending or vice versa.
- Changing a public property's type, mutability, or visibility.
- Removing or changing a default-value parameter such that recompilation is required for callers.
- Removing or changing the value/structure of a public `@JvmInline value class`.
- Changing the parent class or implemented interface set of a public class.
- Removing a default method from an interface (Kotlin compiles `default` differently than Java; check the binary form).

Adding new public symbols, adding new optional parameters with default values, adding new sealed-hierarchy members in a `sealed class` (this **is** breaking for exhaustive-when consumers — list it as breaking), and tightening internal-only behaviour are categorized in the ABI report.

### Internal vs public

The library MUST mark non-public surfaces as `internal` or place them in a `*.internal.*` package. The `verify-release-readiness-library` skill flags any `public` symbol in an `internal` package, and any non-`internal` symbol that the project intends to keep private.

A library that exposes a Kotlin-only API SHOULD use `kotlinx.binary-compatibility-validator` and commit the `api/` baseline files. The plugin uses these baselines as the source of truth for `produce-abi-report`.

### Deprecation policy

When deprecating a public symbol:

1. Annotate with `@Deprecated(message = "...", replaceWith = ReplaceWith("..."))` — `replaceWith` is mandatory if a successor exists.
2. State the **sunset version** in the message: `"Use newApi(). Will be removed in v2.0."`.
3. Set `level = WARNING` initially. Bump to `level = ERROR` one minor version before removal. Bump to `level = HIDDEN` in the version that removes it (the binary signature stays, the source-level reference becomes invisible).
4. Add a `### Deprecated` entry to CHANGELOG with the sunset version.
5. Run `/abi-check` after deprecation to confirm the ABI is still backwards-compatible.

The release-coordinator refuses to publish a major version that removes a symbol unless the symbol has been at `level = ERROR` for at least one prior release.

### POM / publish hygiene

For every published artifact, the POM MUST contain:

- `developers` block with at least one developer with name + email.
- `scm` block pointing at the source repository.
- `licenses` block with a recognised SPDX identifier.
- `description` and `url`.
- Sources jar (`-sources.jar`) and javadoc/dokka jar (`-javadoc.jar`).
- No `-SNAPSHOT` dependencies in the resolved configuration. The plugin probes via `./gradlew dependencies` and rejects.

Signing: every artifact MUST be GPG-signed when publishing to Maven Central. The `check-publish-config` skill verifies signing is configured (env var or `signing.gnupg.keyName` property) but does NOT extract the key — that stays in the user's environment.

## Anti-patterns (both tracks)

- **Skipping `--no-verify`** on tag commits. Tags must pass the readiness check; if it fails, fix the cause, don't bypass.
- **Editing an applied changeset** to "fix" a release. Use `/add-migration` for a corrective changeset (service) or `/deprecate-api` followed by replacement (library).
- **Cherry-picking commits onto a release branch without bumping**. The release branch's last commit MUST be a tag-bump commit; cherry-picks land via PR, not direct commit.
- **Publishing a `-SNAPSHOT` to a release repository**. Snapshots go to a snapshot repository; releases go to a release repository. The plugin refuses to publish if the version contains `-SNAPSHOT` to a release target.
- **Mixing tracks**. A repo MUST be either service or library, not both. Multi-module releases (one repo with N libs + 1 service) are out of scope for v1; track is per-project.
