# CLAUDE.md — komdosh-dev-spring-avro

This plugin owns the **autogenerated event-DTO pipeline** for Kotlin/Spring services. It sits upstream of [`komdosh-dev-spring-events`](../komdosh-dev-spring-events/CLAUDE.md): the events plugin writes consumer logic against generated DTOs; this plugin produces those DTOs and the schemas behind them.

## What it adds

| Surface | Item | What it does |
|---|---|---|
| Agent | [`avro-schema-author`](agents/avro-schema-author.md) | Writes `.avsc` files per `rules/avro-schemas.md`. Picks the right module (inbound vs outbound adapter), the right namespace, the right logical types. Verifies codegen runs and the generated DTO lands where the hexagonal rules say it should. Hands off to `build-expert` (in core) for any Gradle edit and to `event-consumer-author` (in events) when the new schema needs a consumer. |
| Command | [`/avro-new-event`](commands/avro-new-event.md) | End-to-end "add a new event" — toolchain detection → schema authoring → codegen verification → registry-subject guidance → optional consumer scaffold hand-off. |
| Command | [`/avro-evolve`](commands/avro-evolve.md) | Compat-aware schema bump. Classifies the proposed change as additive / borderline / breaking. Bumps in place for additive; produces a v2 schema and new topic name for breaking changes (per the events plugin's "version the topic, not the message" rule). |
| Command | [`/avro-audit`](commands/avro-audit.md) | Read-only Avro health check. Scans `.avsc` files, Gradle wiring, registry config. Output: BLOCKER / WARNING / INFO findings, mirroring `komdosh-dev-spring-security`'s report shape. |
| Skill | [`discover-avro-toolchain`](skills/discover-avro-toolchain/SKILL.md) | Detects which Avro plugin and which Schema Registry SDK are on the classpath. Returns a structured verdict. |
| Skill | [`verify-schema-compat`](skills/verify-schema-compat/SKILL.md) | Compares a proposed schema against its previous version. Returns `BACKWARD` / `FORWARD` / `FULL` / `BREAKING` plus the changed fields. |
| Rule | [`rules/avro-schemas.md`](rules/avro-schemas.md) | Authoring rules — naming, doc requirement, nullability convention (T-first union), logical types, enum vs string, evolution semantics, forbidden patterns. |
| Rule | [`rules/avro-codegen.md`](rules/avro-codegen.md) | Gradle wiring (davidmc24 default; Confluent + avro4k alternates), source paths, generated-DTO placement under `adapters/*/dto/`, Kotlin-from-Java interop. |
| Rule | [`rules/avro-registry.md`](rules/avro-registry.md) | Confluent + Apicurio integration — subject naming strategy, compatibility mode, Spring Boot config snippets, secret handling, the auto-register policy. |

## Boundary

This plugin **owns** schemas and the generation pipeline. It does NOT:

- Write consumers or producers. Consumers are `event-consumer-author` in the events plugin. Producers are `backend-implementer` plus the outbox pattern documented in core's [`rules/persistence.md`](../komdosh-dev-spring-core/rules/persistence.md).
- Modify Gradle files directly — every Gradle edit is delegated to `build-expert` (core).
- Write tests — generated-DTO test scaffolding goes to `test-writer` (core).
- Operate the Schema Registry (push/delete/promote subjects in production) — this is a deployment-time concern; the plugin only configures it.

## Dependencies

This plugin requires `komdosh-dev-spring-core`. It reads:

- `read-service-context` skill (core) — to find module layout and base package before writing schemas.
- `build-expert` agent (core) — for any Gradle plugin or dependency change.
- `test-writer` agent (core) — for tests around generated DTOs.
- The hexagonal rules in core — generated DTOs land under `adapters/`, never `domain/` or `application/`.

It complements `komdosh-dev-spring-events`: that plugin's [`agents/event-consumer-author.md`](../komdosh-dev-spring-events/agents/event-consumer-author.md) already says *"if a registry is configured, the DTO is generated — do NOT hand-write the class"*. This plugin is the answer to "how is it generated?".
